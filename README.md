# qmtIDE-deepseek · v1

**A 股 AI 产业链量化交易系统** —— 日线定方向、分钟线管执行，真实资金实盘运行。

> 不是「预测涨跌」的系统。它的 alpha 形态是**低暴露 + 长骑行 + 深回撤**：
> 大部分时间不参与，参与时集中持有最强 3 只并让盈利奔跑，代价是单段回撤较深。
> 真价值在**风控与不参与**，不在收益率数字。

```text
版本      v1（架构冻结）           执行    大 QMT + 文件桥（bridge）
模式      live 真实资金            行情    tushare（替代源，真实价）
宇宙      43 只固定 + 375 只动态池  持仓    max_positions = 5，T+1
测试      1079 例                 区间    2023-02 → 2026-11
```

---

## 一、它是什么，不是什么

**是**：一套**单账户、单策略、日线驱动**的实盘系统。每天只回答三个问题——今天该不该参与、参与哪几只、什么时候退出。不参与时什么都不做。

**不是**：
- 不是高频/日内系统（`T1_RESTRICTION=True`，当日买入当日不可卖）
- 不是多策略轮动框架（v1 只有一个策略内核）
- 不是选股推荐工具（没有对外服务、没有订阅、不荐股）
- 不是「收益最大化」系统（它主动放弃大部分交易机会）

## 二、系统架构（v1，冻结）

```text
┌──────────────┐   HTTP 只读   ┌────────────────────────────────────────────┐
│  统一看板     │◄─────────────│              live 引擎（:5000）             │
│  :5002       │              │                                            │
│  live+paper  │              │  ① 行情层   tushare → 日线/分钟/宽度        │
└──────────────┘              │  ② 策略层   动量选股 + trend 闸门 + 退出    │
        ▲                     │  ③ 风控层   MDD / 日内 / 连亏 / 单仓上限    │
        │ HTTP 只读           │  ④ 执行层   Broker 抽象 → 文件桥            │
┌──────────────┐              │  ⑤ 账本层   SQLite + 权益快照 + 成交回放    │
│  paper 引擎   │              └──────────────┬─────────────────────────────┘
│  :5001       │                             │ signal.json / result.json
│  100 万虚拟   │                             ▼
└──────────────┘              ┌────────────────────────────────────────────┐
                              │  大 QMT 客户端（XtItClient.exe）            │
                              │  ├ 内嵌 qmtide_bridge.py（Python 3.6.8）    │
                              │  ├ 轮询 signal.json → passorder            │
                              │  └ 回写 result.json + heartbeat.json       │
                              └────────────────────────────────────────────┘
```

**五个模块的职责边界就是 v1 的冻结内容**，改动走缺陷修复流程，不做架构级重构。

| 层 | 目录 | 职责 | 不做什么 |
|---|---|---|---|
| 行情 | `data/` | 拉取、缓存、交易日历、宽度统计 | 不做预测、不用合成价兜底 |
| 策略 | `strategy/` | 选股、信号、退出规则 | 不下单、不读账户 |
| 风控 | `risk/` | 回撤预算、单仓上限、熔断 | 不决定买什么 |
| 执行 | `core/` | Broker 抽象、桥客户端、重连 | 不含策略判断 |
| 账本 | `storage/` | 状态持久化、成交与快照 | 不修正业务规则 |

## 三、执行通道：为什么是「大 QMT + 文件桥」

**起因**：QMT 2.1.32.0 的进程白名单会把外部 Python 判成 `illegal pid`，`xttrader` / `xtdata` 全部不可用。因此交易改由**文件桥**完成——策略跑在 QMT 进程内部，外部引擎只通过 JSON 文件与它通信。

**链路**：

```text
引擎  ──写 signal.json（action / code / side / qty / price / signal_id）──►  QMT 内桥
      ◄──读 result.json（status=ok|error + data）─────────────────────────┘
      ◄──读 heartbeat.json（ts / pid / rev，每 500ms 刷）─────────────────┘
```

**四条设计约束**（都是踩出来的）：

1. **桥内嵌 Python 3.6.8** —— 只用 3.6 语法；`simpleRun="0"` 才会调 `init + passorder`
2. **部署 ≠ 生效** —— QMT 只在「运行策略」时加载 `.py`；`CODE_REV` 写进心跳，重载前后必须**逐字符不同**才能验收
3. **幂等必须落盘** —— `processed_ids.json` 记录已处理 `signal_id`，只有 `status=="ok"` 才入黑名单
4. **存活判定看心跳，不看进程名** —— 心跳新鲜 = QMT 已登录 + 策略已运行 + 桥已 init

```bash
python scripts/bridge_health.py
# [bridge] OK rev=2026-11-09T1125-write-retry pid=10900 age=1.0s
```

## 四、双区隔离：live 与 paper 同时跑

| | live | paper |
|---|---|---|
| 资金 | 真实 | 100 万虚拟 |
| 端口 | 5000 | 5001 |
| 账本 | `storage/qmt.db` | `storage_paper/qmt.db` |
| 日志 | `logs/` | `logs_paper/` |
| 交易通道 | 文件桥 | `_NoTradeBroker`（**真实下单硬阻断**） |

隔离由 `core/zone.py` 单一推导（`--zone` > `QMT_ZONE` > live），不靠手工改环境变量。paper 区只有一个意义：**在同样行情下观察信号质量**；它的绝对收益不可与 live 横向比较。

```bash
scripts\run_live.bat      # 拉起 live 引擎，并自动带上 5001 + 5002
scripts\run_zone.bat      # 只拉起观察区 + 看板（幂等，按端口判定）
```

## 五、策略内核

**入场是五个条件的合取**（全部满足才买）：

| 条件 | 参数 | 当前值 |
|---|---|---|
| 动量排名进 Top N | `momentum_top_n` / `momentum_lookback` | 3 / 60 |
| 动量下限（60 日涨幅） | `momentum_min_mom` | +15% |
| 趋势向上（收盘站上 MA60 等） | — | **弱市里真正的绑定点** |
| 宽度确认（至少 N 只同时通过） | — | 2 |
| 大盘日偏置 | `min_daily_bias` | 2.0 |

**退出**（`exit_mode="trend"`）：趋势破位 + ATR 止损（`atr_stop_mult = 2.9`）+ 单日暴跌清仓（`down_day_exit_pct = −3.25%`）。

**仓位**：`risk_per_trade = 4%`、单标的 ≤ 40%、`max_positions = 5`。三者名义上限 200%，实际由 `max_positions` 与 ATR 共同夹紧。

**不参与也是一种仓位**：2026-04 → 2026-10 弱市期连续零买入是**设计行为**，不是故障。同一区间回测权益同样零变动 —— 回测与实盘行为一致。

> **已证伪的方向不重试**：参数空间（36 个轴）已闭合或已定价；KPI「正收益折数」被证明是划分依赖型噪声，禁止当优化目标。清单见 `reports/OPEN_DECISIONS.md`。

## 六、风控三段

| 段 | 机制 | 触发后行为 |
|---|---|---|
| 事前 | 单仓上限 40% / `max_positions=5` / T+1 | 拒绝下单 |
| 事中 | 日回撤、连亏计数、大盘日偏置 | 降仓位系数 / 停新开仓 |
| 事后 | MDD 硬上限 −20% / 日暴跌清仓 | **只减仓、不加仓** |

**不可放松的三条**：`MDD −20%`、`T1_RESTRICTION=True`、`ALLOW_MOCK_TRADING=False`。任何自动化（含自进化）不得修改这三项，也不得把 `EXECUTION_MODE` 切为 live —— 切换只能人工完成。

**估值口径是风控的前置条件**：live 只认券商权威总资产，取不到就返回 `None`，绝不用本地拼装顶替。历史事故：拼装口径把总资产算成纯现金，风控据此判出 −89% 假回撤，触发真实强平。

## 七、数据与账本纪律

- `equity_snapshots` 是**权益曲线唯一事实源**；`eod_is_close=true` 的快照才可当收盘，盘中值不可跨日比较
- `fills` 是**成交唯一事实源**；「现金没变」不能反证没有隐藏成交
- 引擎状态单行（`engine_state`），重启后必须能恢复风控四字段（`peak_asset` / `consec_loss` / `halted` / `daily_trade_count`）
- 持仓的 `open_date` 券商不返回，由 `fills` 最近一笔买入回灌 —— 否则 T+1 与建仓保护期对实盘双双失效

## 八、工程纪律

| 项 | 规则 |
|---|---|
| 测试 | `python tests/run_all.py` —— **1079 例**（含 33 条历史遗留失败，清单见 `reports/`） |
| 守卫测试 | 每条实盘缺陷修完必须补一条**反向断言**，防止后人把补丁写成「问题已解决」 |
| 部署 | 改 `.py` **必须重启**才生效（全仓无 `importlib.reload`）；桥改完必须点「停止策略 → 运行策略」 |
| 提交 | 本地 commit → 全量测试 → 密钥/账号扫描 → 人工确认后 push |
| 脱敏 | 仓库 public：日志摘录入库前必须过账号脱敏（密钥扫描认不出账号） |

**两条反复踩到的仪器错误**，已写进测试模板：

1. **比对的双方不是同一坐标系** —— 工作区 CRLF、`git show` 是 LF，逐字节比对必然报假
2. **`timeout /t` 在无控制台时立即返回** —— 等待循环会空转并打出假告警，改用 `ping -n`

## 十一、v1 版本边界

**v1 的承诺是「稳定」，不是「更多功能」。**

会做：
- 缺陷修复（资金安全级优先）
- 运维可靠性（启动、自启、体检、告警）
- 取证与审计（每条修复留下可复核的证据）

不会做（留给 v2）：
- 架构级重构（模块拆合、换引擎、加消息队列）
- 多策略框架 / 策略动态切换
- 引入新的执行通道或第二套行情源
- 在已证伪的参数方向上重扫

**判断标准**：一个改动如果会让「回测结论与实盘行为的一致性」变得不可验证，它就不属于 v1。

## 十二、已知缺陷（v1 未修，按风险排序）

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | 幻影单：`passorder` 成功但拿不到 `order_id` 时，引擎判成功 → 建幻影仓 → 下一轮归零 → 信号重现 → 二次下单 | 重复买入；每次还 +1 日交易计数，30 秒可刷满 `max_daily_trades`，当日买入闸门关死 |
| 2 | broker 断链期，持仓不受退出逻辑管理 | 断链时止损/趋势退出不作用于真实仓位 |
| 3 | `_peak_equity` 每次 live 重启归零 | 面板回撤偏乐观，−20% 硬线的实际触发位偏低 |
| 4 | `daily_loss_limit_pct` 被 `max(5000, 3%)` 覆盖 | 写成 −3%，实际按约 7.5% 生效 |
