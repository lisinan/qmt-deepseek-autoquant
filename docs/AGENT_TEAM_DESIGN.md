## 一、为什么是「五岗 + 一条文件总线」而不是「十个任务」

2026-10-29 切 live 后的实证：**10 个定时任务里有 5 个因各自 prompt 里的门禁把自己停掉了，
互相不知情，真实资金账户连续 2 个交易日没有盘前体检和盘后复盘**；而 METRIC-HYGIENE 在 17:36
就写出了「持仓估值退化为 avg_cost、同一天四个总资产口径、8,931 触发假熔断」这条资金安全级发现，
**却没有任何环节去消费它**。

⇒ 两个结论决定了本设计：

1. **碎片化任务 ≠ 分工**。任务越多，越容易「各自停机 + 结论无人消费」。分工应该落在**角色**上，而不是落在**时间槽**上。
2. **状态必须放文件，不能放对话**。跨任务、跨会话能传递的只有仓库里的 `reports/ / logs/ / docs/`。所以架构的核心是一条**文件总线**，而不是消息总线。

## 二、整体架构

```
                    ┌──────────────────────────────┐
   人（唯一权力源）  │  OWNER：改参数 / 切模式 / 重启 / push │
                    └───────────────┬──────────────┘
                                    │ 指令 + 裁决
                    ┌───────────────▼──────────────┐
   L1 编排层         │ 主理人 何执舟（首席策略官）    │  唯一对外出口
                    │ 拆解 · 调度 · 交叉 · 裁决      │  不做分析、不代写
                    └───┬───────┬───────┬───────┬──┘
        ┌───────────────┘       │       │       └───────────────┐
   L2 专业层（域不重叠，跨域只经主理人中转）
   ┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐
   │甄有据 研究 │ │魏守线 风控 │ │常在线 实盘 │ │舒对账 账本 │ │毕提交 交付 │
   │验证/KPI/周期│ │预算/合规/否决│ │成交/估值/存活│ │口径/三态  │ │测试/commit │
   └─────┬──────┘ └─────┬──────┘ └─────┬──────┘ └─────┬──────┘ └─────┬──────┘
         └──────────────┴───────┬──────┴──────────────┴──────────────┘
                    ┌───────────▼──────────────────────────┐
   L3 执行层         │ 定时流 3 槽（15:40 / 周日 20:00 / 21:00）│
                    │ 事件流 1 类（P0 资金安全，抢占式）        │
                    │ 人机流 1 类（OWNER 提问）                │
                    └───────────┬──────────────────────────┘
                    ┌───────────▼──────────────────────────┐
   文件总线          │ reports/（结论+INBOX） logs/（账本+心跳） │
   （唯一跨会话状态） │ docs/（契约+决策）  storage/（数据，不入库）│
                    └──────────────────────────────────────┘
```

三层职责一句话：

- **L0 OWNER**：唯一有权改生产参数、切 `EXECUTION_MODE`、重启、push、下单的人。
- **L1 主理人**：把问题拆成正确的分工、逼出带证据的结论、在冲突时做唯一裁决。
- **L2 五岗**：各守一个分析域，输出「结论 + 证据 + 不知道的部分」。
- **L3 调度**：时间触发为主，事件触发抢占，人工触发兜底。**L3 不产生新职责，只复用 L1/L2 的 SOP。**

## 三、模块分工（含权限边界）

| 角色 | Agent ID | 分析域 | 输入 | 输出 | 写权限 |
|---|---|---|---|---|---|
| 首席策略官 | `quant-ops-team-team-lead` | 编排与裁决 | 成员回传、契约、INBOX、OPEN_DECISIONS | 裁决结论（结论/代价/反证/生效方式） | 报告、INBOX 路由 |
| 策略研究官 | `strategy-researcher` | 信号有效性、验证设计、KPI | 已证伪清单、参数审计、面板数据 | 四窗 + 逐折指纹 + 判定 | `reports/`、`strategy/` 研究代码 |
| 风控审计官 | `risk-controller` | 回撤预算、杠杆合规、最坏情景 | 研究官原始数字 | 通过/有条件/否决 + 三笔账 | 风控报告、INBOX 的 FORBIDDEN 行 |
| 实盘链路工程师 | `live-ops-engineer` | 委托成交、估值口径、存活判据 | 券商回报、`guardian.log`、`engine_stdout.log` | 活体结论 + 链路数字 + 口径差异 | 诊断报告、只读脚本 |
| 账本与量测审计官 | `data-ledger-auditor` | 账本口径、EOD 新鲜度、活性三态 | `evolution_ledger.jsonl`、槽位表 | 三处对账 + 三态 + 归因 | 账本修复脚本、量测报告 |
| 交付与版本工程师 | `release-engineer` | 代码落盘、测试、提交、密钥 | SAFE 项 | commit hash + 测试计数 + 生效核验 | `.py`/测试/文档、本地 commit |

**为什么是这五个而不是更多**：判据是「有没有人会直接问它」。
- 「这段为什么亏」→ 研究官；「越没越过线」→ 风控；「单为什么没成交」→ 实盘；「账为什么对不上」→ 账本；「代码怎么落」→ 交付。
- 拆分到此为止：再拆（比如单列一个「因子工程师」）就会出现「用户不会直接问、只能被主理人调用」的岗位，那属于研究官域内的能力，不配独立席位。
- 反过来，把风控并进研究官是**最危险的合并**：否决权与研究动机必须分离，否则「Sharpe 好看」会自己给自己放行。

## 四、任务流转机制

### 4.1 三种流

| 流 | 触发 | 编排 | 终止条件 |
|---|---|---|---|
| 定时流 | 交易日 15:40 / 周日 20:00 / 周日 21:00 | W1 日度复盘 / 周度深度 / 二阶改进 | 产物落盘 + INBOX 写入 + memory 一行 |
| 事件流 | P0：估值失真 / 假熔断 / 强平 / 委托被拒 / 引擎消失 | 抢占：先止血（只读诊断 + 报告），再并入当日复盘 | P0 出现在首屏且已路由 |
| 人机流 | OWNER 提问 | 单域直调成员；跨域走 W1~W4 | 主理人给出裁决 |

### 4.2 四 Phase 交接（以 W1 为例）

```
P0 清场（主理人亲自，不派活）
   读契约 → 读 INBOX → 读 OPEN_DECISIONS → 读上一篇复盘
   产出：3 行「我看到的状态」+ 今日属于哪条流
        │
P1 并行取证（同一消息 spawn，互不依赖）
   live-ops ── 估值/成交/存活 ──┐
   ledger   ── 账本/EOD/三态  ──┼──→ 各自回传「结论+证据+不知道」
   research ── 开仓归因/零BUY ──┘
        │  （原文整段传递，不摘要）
P2 串行交叉
   risk-controller 做否决式审查：最坏会怎样、越没越过 −20% 预算
        │
P3 裁决（主理人）
   结论 / 代价（最差折·Calmar·预算使用率）/ 反证 / 生效方式
        │
P4 交付
   报告 → INBOX 行 → P0 首屏 → SAFE 项交 release-engineer（改→测→本地 commit，不 push）
```

**交接物的硬要求**：每一棒必须传**原文**。历史上「把结论摘要传给下一棒」直接导致风控在不知道
「这个 Sharpe 是拼接口径」的情况下放行。

### 4.3 单域 vs 跨域的路由

| 问法 | 路由 |
|---|---|
| 只涉及一个域 | 直调该成员，主理人不插手内容 |
| 跨两个以上域 / 要拍板 / 涉及真实资金 | 走 Workflow，主理人编排 |
| 涉及改参数、切模式、重启、push | **任何流都不执行**，只产出「一键生效方式」交给 OWNER |

## 五、调度与触发规则

### 5.1 现状映射（不新增任务，先把角色挂到已有槽位）

| 槽位 | 任务 | 主责成员 | 副责成员 | 为什么这个时间 |
|---|---|---|---|---|
| 交易日 15:40 | DAILY-REVIEW | 实盘 + 账本 | 研究 + 风控 + 交付 | 收盘后 40 分钟，DB 快照已落、引擎已停手 |
| 周日 20:00 | SYNTHESIZE | 研究 | 风控 + 账本 | 周末白天机器易休眠（10-31 两次休眠致任务全丢），夜间更稳 |
| 周日 21:00 | RECURSIVE（RSI） | 主理人 + 账本 | 交付 | 接在 SYNTHESIZE 之后，改流程本身 |

### 5.2 四条调度纪律（缺一条就会产生假绿）

1. **交易日语义**：非交易日不产生槽位（`core/market_calendar.is_trading_day`）。休市日不得判漏跑。
2. **产物贴槽位**：产物时间戳必须落在「槽位后 0~4 小时」。用「到 now 为止」会把次日补跑洗成正常。
3. **幂等**：同一槽位只产出一份带日期产物；重跑覆盖不追加。
4. **空转留痕**：什么都没做也要写一行「本轮无动作 + 原因」。否则下一轮无法区分「没跑」和「跑了没做事」。

### 5.3 活性判定（禁止「最近运行时间」单指标）

三态 + 三归因，实现只有一份：`scripts/_loop_liveness.py`（主审计脚本只 import，不得自带第二份判据）。
归因决定修复对象：`prompt_gate`→改 prompt；`machine_sleep`→改时段/别关机；`awake_no_artifact`→查宿主。
判据细则见 `AUTOMATION_CONTRACT.md §4.2`。

### 5.4 建议补一个槽位（待 OWNER 裁决，本文不擅自创建）

**交易日 09:05 静默体检**（只读、无 LLM 重活）：昨日改动 `源码 mtime < 进程启动时刻` 核验 +
`EXECUTION_MODE` 一致性 + 引擎存活。理由：当前「昨晚改了代码、今早带旧代码开盘」要到 15:40 才发现，
而 15:40 已经用真实资金跑完一整天。代价：多一个任务、多一份活性审计负担 —— 所以只在**做需要重启的改动的次日**触发更划算（可用一次性任务替代常驻）。

| 团队通用打法 | 专家包内置 `quant-ops-playbook` | 调度与活性、晋升闸门、GitHub 纪律；只写「怎么用」，数字仍读契约 |

## 七、GitHub 联动

### 7.1 边界

| 动作 | 谁可以 | 说明 |
|---|---|---|
| 改代码 + 本地 commit | 交付工程师 | 需 SAFE 项出处 + `run_all` 全绿 + 密钥扫描 |
| `git push` | **仅 OWNER 指令** | 自动化与成员 agent 一律不 push（契约 §二.3） |
| 改 `config/settings.py` 生产参数 | 仅 OWNER | 团队只给「字段+目标值+生效方式」 |
| 重启引擎 | 仅 OWNER | 团队只核验 `mtime < 启动时刻` |

### 7.2 什么进仓库

进：`*.py`、`tests/`、`docs/`、`reports/*.md`、配置模板。
不进：`storage/*.db`、`*.pkl`、`.env`、`logs/*.log`、`storage/dynamic_universe.json`（按先例留本地）。

判据：**clone 下来能跑 + 结论能复查**。数据与密钥都不满足。

### 7.3 commit 语义 = 决策日志

`<type>(<scope>): <中文一句话>`，正文写「现象 / 根因 / 验证方式」，涉及轮次带 `R##`。
这样 `git log` 本身就是一部可审计的策略变更史 —— 比任何报告目录都可靠，因为它不可篡改（有 hash）。

## 八、围绕「优化策略 / 控制风险 / 提升收益」的闭环

### 8.1 明确不做什么（这是设计的一半）

- **不再投单参数网格**：4 个负折全部落在 2026-04-23~10-21、前 22 折全正 ⇒ 周期依赖，不是参数缺陷。
- **不把「正收折数」当目标**：同一条 +218.8% 曲线，切 9 段说 77.8%、切 2 段说 50.0%，是划分依赖噪声。
- **不靠降级风控换平滑**：买入侧冻结类风控（连亏/日亏/权益回撤暂停）已有 3 条同向证据显示**反而放大 MDD**。

### 8.2 只做三件事，每周一步

| 主线 | 做什么 | 产出 | 判据 |
|---|---|---|---|
| A 弱市期诊断 | 拆 2026-04-23~10-21 的市场结构：`trend_up` 四条件哪一条是杀手、宇宙动量分布、信号断层 | 诊断报告 + 可证伪假设 | 能解释「为什么 22 折全正、4 折全负」 |
| B 实盘口径对账 | 每轮先审「实盘有、回测无」的分支 | 口径缺陷清单 + 修复 | 历史收益最高的方向（4 个 P0/P1 全出自这里） |
| C 二阶改进 | 守卫、度量、活性、防误诊 | 一条守卫测试 | 让下一轮更可能做对 |

### 8.3 收益提升的唯一合法通路

```
发现口径缺陷（B） → 修复 → 暴露恢复/成本下降 → 收益改善
发现周期结构（A） → 接受「下降市不参与」 → 减少无效交易与回撤 → Calmar 改善
```

**没有第三条路。** 任何号称「调参提高收益」的方案，先过四道闸门（最差折 / 主口径 / 质量 / 结构），
且必须回答「这次改动值多少 dSh、多少 pt 收益、多少预算使用率」。

### 8.4 风险控制三层

| 层 | 机制 | 负责人 |
|---|---|---|
| 事前 | 四道晋升闸门 + 杠杆上限（`risk_per_trade` 已≈2.24×，不许再叠）+ 现金可成交性检查 | 风控 |
| 事中 | `core/guardian.py` 300s 心跳 + 熔断（**必须用券商真实口径**）+ 单仓/单笔上限 | 实盘 + 引擎 |
| 事后 | 账本 `eod_is_close` 检查 + 三处对账 + P0 首屏 + INBOX 消费 | 账本 + 主理人 |
