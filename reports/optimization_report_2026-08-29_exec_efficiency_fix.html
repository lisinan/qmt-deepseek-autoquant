2 · 根因诊断

实时引擎此前每 ~0.3s 在主循环抛一次 OSError: [Errno 22] Invalid argument，并把它当作业务异常以完整 traceback写入日志，CPU 被反复计算 traceback 白白烧掉。逐层定位：

  • engine/event_engine.py:985 在 _evaluate_sectors 的 except 里 logger.warning("sector 评估失败: %s\n%s", e, tb_str) —— 把全量 traceback 每轮刷进日志（日志膨胀 + CPU 主因）。
  • 异常真正来源：后台化的引擎进程，其 stdout/stderr 是已失效的管道，任何向其 write 的操作都会抛 OSError [Errno 22]。该异常从 sector_scorer.evaluate_sectors 内部冒出，被上层当业务失败捕获。
  • 既有 _SafeStreamHandler（H/I 轮加入）只兜住了 logging 自身写 stdout 的失败，未兜住「用户代码直接写破损 stdout」这一路径，故缺陷仍在。

3 · 本次修复（源码层，非收益参数）

  • main.py · 全局安全流：新增 _BrokenPipeSafeStream，在 _setup_logging 启动时把 sys.stdout/sys.stderr 包成「写失败也不抛异常」的流；并设 logging.raiseExceptions = False，彻底压制任何 handler 异常的 traceback。直接 print() 或 logging 写破损管道都不再上抛。
  • event_engine.py:982：sector 评估异常改为单行 logger.warning("sector 评估失败: %s", e)，完整 traceback 仅留 DEBUG 级别 —— 不再每轮刷屏。
  • event_engine.py · _log_reject_once：拒绝日志增加 60s 时间节流（同一 标的+原因 至少 1 分钟记一次），消除「daily_trades>10」每轮重复刷 INFO 的问题。

三项改动均为工程健壮性，不触动任何策略/收益逻辑；生产配置（trend + vol + max5，regime off）保持不变。
