## 二、专项：#3 那条「宇宙 4 只」的漏斗行是怎么来的

14:48:57 的日志序列（同一秒内）：

```
14:48:18  engine.event_engine: 检测到外部停止信号（STOP_ENGINE），正常退出
14:48:22  Engine 启动: mode=single data=xtdata broker=disconnected exec=paper codes=38
14:48:57  engine.event_engine: 正在刷新日线多周期上下文...
14:48:57  [WARNING] 无入场信号 ... | 漏斗分层: 宇宙 4 只, trend_up 0, ...
14:48:57  strategy.daily_context: DailyContext 刷新完成: 38/38（本次网络拉取 36，累计覆盖 38 只）
```

**成因（已定位，非数据源问题）**：引擎重启后存在**「漏斗先于日线上下文就绪被计算」的时序竞态** —— 那一次漏斗读取的是尚未刷新的上下文（仅剩 4 个指数级缓存），日线刷新完成（38/38）的日志落在同一秒的**更晚**位置。

**危害**：该行在文本上与真行**无法区分** —— 它同样带 `trend_up 0 / bias 0 / score 0` 的合理外观，只有「宇宙 4」这一个数字露馅。这正是 2026-10-28「全天 25 条逐字节相同」教训的同型缺陷：**日志不携带上下文就绪度，事后只能靠肉眼比对 13 行才能发现基数是假的**。

**处置建议（不自行改码）**：
1. 漏斗行增加 `feat_asof=<bar 日期>` 与 `stale_n=<滞后交易根数>`，并附 `universe_ready=<就绪只数>/<订阅只数>`；未就绪时降级为 DEBUG 或不输出。
2. 或最低成本：上下文未就绪（就绪只数 < 订阅只数）时直接跳过本次漏斗输出。

## 四、今日最该修的一条量测卫生问题

**引擎重启后「漏斗先于日线上下文就绪被计算」，产出基数造假的漏斗行（今日 1/13 条为「宇宙 4 只」假基数），且日志不携带 `feat_asof` / `stale_n` / `universe_ready` 使真假行在文本上不可分辨。**

理由：其余告警都是「数据旧」——旧而可知、可查、可复算；而这一条是**「看着像真的假数据」**。它直接继承 2026-10-28 的教训：当天 25 条漏斗行逐字节相同，正是因为没有字段能揭示快照的数据日期与就绪度，才会在研究侧复算差一个数量级之后才被发现。今日 trend_up 复算差值为 0 属**运气**（上下文在下一轮已补齐、且当日趋势结构未变），不是机制保证 —— 一旦重启发生在临界时点，同样的日志会输出一个「合理但错误」的漏斗，而我们不会知道。

成本最低的修法：漏斗输出前加一道 `universe_ready == subscribed` 的就绪断言，并把 `feat_asof` 写进日志行。**建议列入 17:00 工程维护，由人确认后实施。**
